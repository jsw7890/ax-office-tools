# 설계서: 사내 챗봇 · 회의실 예약 · 헬프데스크 (최소 기능 버전)

상태: v0.4 (2026-11-26, 챗봇 고도화 2단계: 벡터+키워드 혼합 검색) (Claude 단독 설계). 변경 내용은 13장 / 원본: Claude Docs 설계서(2026-11-06)
Cursor는 이 문서를 고치지 않는다. 설계와 달라지는 필요가 생기면 docs/handoff/requests/ 에 요청 파일로 알린다.

## 1. 목적과 원칙
- 직원 약 50명이 쓰는 웹앱 하나에 세 기능을 최소 기능으로 만든다. 취업용 레퍼런스이므로 실제 회사 데이터는 쓰지 않는다.
- 한 앱 · 한 DB · 한 로그인을 공유한다. 그래야 챗봇이 회의실·문의 데이터를 읽을 수 있다.
- 3장에 적은 "하지 않는 것"은 만들지 않는다.
- 비용 발생(LLM 호출 포함), 비밀키, 보안 설정, 배포는 사람 승인 없이 하지 않는다.

## 2. 기술 선택 (제안, 검수 때 확정)
| 구성 | 선택 |
| --- | --- |
| 화면 + 서버 | Next.js 웹앱 |
| DB · 로그인 · 권한 | PGlite(이 PC 안에서 도는 Postgres, `.data/` 폴더). 스키마·권한 규칙(RLS)은 `supabase/migrations/`의 SQL을 그대로 쓴다. 로그인은 샘플 계정 2개(직원·관리자). Supabase 이메일 로그인은 붙이지 않았다 |
| 배포 | Vercel (상용 배포는 사람 승인) |
| 챗봇 LLM | 이 PC의 로컬 Ollama (무료, 기본 모델 qwen2.5:0.5b). 유료 API·키는 쓰지 않는다 |
| 임베딩(검색용 벡터) | 같은 로컬 Ollama의 bge-m3(1.2GB, 1024차원, MIT, 질문에 지시문 불필요). 모델 이름은 환경변수 EMBED_MODEL(기본 bge-m3). 모델 내려받기는 사람 승인. 선정 근거: 한국어 검색 순위표(ko-embedding-leaderboard, 2026-07)에서 bge-m3 79.30, qwen3-embedding:0.6b 75.88. 한국어 미세조정 모델(KURE-v1)은 Ollama 공식 배포가 없어 제외, qwen3-embedding:4b(2.5GB)는 이 PC 메모리를 고려해 2단계 기준 미달일 때만 검토 |
| 벡터 저장·검색 | PGlite의 pgvector 확장(`@electric-sql/pglite-pgvector` 0.0.16, PGlite 0.5.15와 맞는 버전으로 고정) |

## 3. 범위
| 모듈 | 하는 일 | 하지 않는 일 |
| --- | --- | --- |
| 사내 챗봇 | 규정 질문에 답하고 근거 조항 표시. 회의실 예약·취소와 IT 문의 등록을 제안하고 확인 버튼을 누르면 저장(7.3). 내 예약·내 문의 조회 | 규정 외 질문, 실제 사내 문서 학습, 대화 기억, 확인 없이 저장 |
| 회의실 예약 | 방별 시간표, 예약·취소, 중복 방지, 시작 10분 전 화면 알림(사용자 설정) | 반복 예약, 승인, 장비 예약, 메일·푸시 알림, 캘린더 연동 |
| 헬프데스크 | 문의 접수, 상태 관리, 댓글, 답변·상태 변경 화면 알림 | 담당자 자동 배정, SLA, 첨부파일, 메일 알림, 자산 연동 |
공통으로 뺀 것: 메일·푸시 알림, 통계 대시보드, 다국어, 실제 회사 규정 사용. 화면 안 알림은 위 두 가지만 있다.

## 4. 폴더 구조
```
docs/        design.md, RULES.md, handoff/
src/         앱 코드 (Cursor)
supabase/    migrations/ (DB 스키마·권한 규칙)
data/regulations/  규정 원문 텍스트와 출처 기록
tests/       테스트 (Cursor)
```

## 5. 공통: 로그인과 권한
- 이메일 로그인 필수. 역할은 staff(직원), admin(관리자) 둘뿐. admin은 총무 등 문의를 받는 사람으로 가정한다.
- 권한 규칙은 화면이 아니라 DB(RLS)로 건다.
  - 직원: 예약·문의는 본인 것만 수정·취소. 시간표 표시를 위해 예약 목록은 전체 조회 가능.
  - 관리자: 방 관리, 전체 문의 조회·상태 변경, 전체 예약 취소.
- API 키는 서버 환경변수에만 둔다. 화면 코드·저장소에 넣지 않는다.

- 질문 로그에는 이름 대신 user_id만 남긴다. 보관 기간은 사람이 정한다(미정).

## 7. 사내 챗봇
### 7.1 규정 자료
- 출처가 분명한 공개 자료만 쓴다. 후보: 고용노동부 표준취업규칙, 국가법령정보센터의 근로기준법 조문. 원문을 내려받아 이용 조건을 확인한 뒤 data/regulations/ 에 텍스트로 저장한다.
- 문서마다 regulation_docs에 발행처·URL·기준일을 기록한다. is_sample=true.
- 화면에 "공개 자료 기반 샘플이며 실제 회사 규정이 아닙니다 / 법률 자문이 아닌 참고용 / 고객·개인정보는 입력하지 마세요"를 상시 표시한다.
- 조항 단위로 쪼개 regulation_chunks에 넣는다(article_no, heading, content).
- 본칙 조문만 넣는다. 부칙, 웹페이지 잔여 코드, 조문 끝에 붙은 다음 장 제목은 지운다. 정리는 다시 실행해도 결과가 같아야 한다.

### 7.2 동작
1. 직원이 질문 한 개 입력 (대화 기억 없음, 질문 하나당 답 하나). 먼저 업무 요청인지 가린다(7.3). 업무 요청이 아니면 아래 규정 답변으로 간다.
2. 서버가 질문과 관련된 근거 조항을 고른다(7.5 혼합 검색). 이 PC의 로컬 LLM(Ollama)이 켜져 있으면 고른 조문만 넘겨 답을 다듬는다. LLM이 꺼져 있거나 실패하면 조문 검색 답을 그대로 쓴다.
3. 답은 전달된 조항만 근거로 하고 문서명·조항 번호를 붙인다.
4. 근거가 없으면 정확히 이 문장으로 답한다: "규정에서 확인되지 않습니다. 관리자에게 문의하세요." 추측하지 않는다.
5. 규정과 무관한 질문은 "규정 질문만 답할 수 있어요."로 안내한다.
6. 답변 아래에 출처 문서·조항·기준일을 표시하고 chat_logs에 저장한다.
- 화면에는 실제 동작(로컬 LLM 사용 여부, 검색 방식이 혼합 검색인지 키워드 검색인지, 꺼지면 조문 검색)을 표시한다. "향후 LLM 추가 예정" 같은 문구는 쓰지 않는다.
- 사용자별 하루 질문 수를 제한한다. 기본값 20회(가정, 사람이 조정).
- 챗봇 코드는 "도구" 추가가 쉬운 구조로 만든다.

### 7.3 업무 처리 (예약·취소·문의)
- 업무로 가리는 것은 요청 표현이 분명할 때만이다(예: "예약해줘", "취소해줘", "등록해줘", "안 켜져요"). 규정을 묻는 문장("연차 예약은 며칠 전에 해야 해?", "회의실 예약 규정 알려줘")은 규정 답변으로 간다. 단어 하나("안", "회의실", "비밀번호")만으로 업무로 가리지 않는다.
- 업무 종류: 회의실 예약, 회의실 예약 취소, IT 문의 등록, 내 예약 조회, 내 문의 목록·상태 조회, 예약 알림 켜기.
- 날짜: 오늘, 내일, 모레·내일모레(+2일), 글피(+3일), 이번 주·다음 주 X요일(주는 월~일), 요일만 있으면 가장 가까운 앞날, M월 D일, M/D, YYYY-MM-DD. 올해에서 이미 지난 월·일은 다음 해. 시각은 "N시 반" = N:30, 1~6시는 오후로 본다. 기준일은 한국 시간이다.
- 날짜나 시각이 없거나 알아듣지 못하면 되묻는다. 오늘로 채우지 않는다.
- 예약·취소·문의 등록은 챗봇이 저장하지 않는다. 챗봇은 무엇을 할지 제안(방·날짜(요일)·시각·제목, 또는 분류·제목)하고, 직원이 화면의 확인 버튼을 누르면 화면이 기존 API(예약 POST /api/reservations, 취소 DELETE /api/reservations/{id}, 문의 POST /api/tickets)를 부른다. 로그인·같은 출처·DB 규칙 검사는 화면에서 저장할 때와 같다.
- 확인 버튼은 한 번 누르면 잠근다. 저장이 실패하면 서버의 오류 문장을 보여 준다.
- 지난 시간과 운영 시간(09:00~18:00) 밖은 제안 단계에서 알린다. 최종 검사는 DB가 한다.
- 취소 후보는 본인의 앞으로 남은 예약(active)만이다. 여럿이면 고르게 한다.
- 내 문의 상태 조회는 질문의 단어(분류·제목)로 찾고, 여러 건이면 목록을 보여 준다. 새 문의를 만들지 않는다.
- 조회와 알림 켜기는 확인 없이 바로 처리한다. 알림 켜기는 "켜", "설정" 같은 요청 표현이 있을 때만이다.
- 업무 처리 결과는 정해진 문장으로 보여 주고 LLM이 다시 쓰지 않는다(틀린 방·시각이 섞일 수 있음).

### 7.4 평가
- `npm run eval`: 평가 질문(tests/eval/questions.json)을 LLM·DB 없이 업무 분류와 조문 검색에 넣어 채점한다. 결과는 변경 전후 비교에 쓴다.
- 평가 질문은 모두 업무로 분류되지 않아야 한다(테스트로 고정).
- 검수용 별도 질문은 Claude가 관리하고 개발·조정에 쓰지 않는다.
- 2단계부터 `npm run eval`은 키워드 검색과 혼합 검색(bge-m3)을 모두 채점하고 나란히 출력한다(상위 1개·상위 3개 정답 수, 범위 밖 거절 수). Ollama나 임베딩이 없으면 혼합 검색 줄은 '미실행'으로 출력하고 실패로 끝내지 않는다.
- 2단계 완료 기준(혼합 검색): 일상어 24개 중 상위 3개 안에 정답 20개 이상, 조문 표현 6개 모두 상위 3개 안, 범위 밖 4개 모두 거절. 미달이면 수치를 그대로 보고하고 기준을 낮추지 않는다.

### 7.5 혼합 검색 (벡터 + 키워드)
- 조각: 조문 하나가 700자 이하면 한 조각, 넘으면 항(①②…) 단위로 나눈다. 각 조각 앞에 "근로기준법 제N조(제목)" 머리말을 붙여 임베딩한다.
- 임베딩 만들기: `scripts/embed-regulations.ts`가 모든 조각의 벡터를 regulation_embeddings에 넣는다. 다시 실행하면 같은 모델의 기존 벡터를 바꾼다. 규정을 다시 넣으면(load-regulations) 벡터가 함께 지워지므로 이 스크립트를 다시 실행한다. DB를 여는 스크립트는 앱을 끈 상태에서 실행한다.
- 질문 처리: 질문을 같은 모델로 임베딩해 벡터 검색 상위 20개 조문(조문별 가장 가까운 조각)과 기존 키워드 검색 결과를 RRF(순위 역수 합, k=60)로 합쳐 상위 3개 조문을 근거로 쓴다.
- 거절: 단어 목록(REGULATION_CUE) 대신 벡터 유사도 기준값으로 정한다. 1순위 조문의 유사도가 기준값 미만이고 키워드 검색도 근거를 못 찾으면 4번 문장으로 답한다. 기준값은 평가 질문으로 정하고 값과 근거 수치를 test-report.md에 남긴다.
- 연소자 전용 조문(15세 이상 18세 미만, 제69조)은 질문이 연소자를 묻지 않으면 혼합 검색 결과에서도 뺀다(지금 키워드 검색과 같은 규칙).
- 되돌아가기: Ollama가 꺼져 있거나, LLM_PROVIDER=mock이거나, 해당 모델의 임베딩이 없거나, 임베딩 호출이 실패·시간 초과하면 지금의 키워드 검색으로 답한다. 이때 오류로 끝내지 않는다.
- 임베딩 호출은 지금 ollama.ts와 같은 규칙(이 PC 주소만, 시간 제한)을 쓴다. 다른 주소로 보내지 않는다.
- 저장소: 벡터는 `.data/`의 로컬 DB에만 있고 저장소에 넣지 않는다.

## 8. 회의실 예약
- 운영 시간 09:00–18:00, 30분 단위 (확정). 종료 > 시작, 예약은 하루 안에서만. 지난 시간은 예약 불가. 본인 예약만 취소(관리자는 전체).
- 화면: 시간표(날짜 선택, 방 × 시간 격자, 예약자 표시) / 예약 입력 창(방·시간 채워짐, 제목 입력) / 내 예약(목록, 취소) / 관리자 방 관리(이름·수용 인원·위치·사용 여부).
- 방 개수는 미정. 샘플 데이터로 3개 방을 넣는다.

## 9. 헬프데스크
- 상태는 접수 → 처리중 → 완료. 완료 후 되돌리지 않고 새 문의를 등록한다. 완료 시 done_at 기록.
- 화면: 문의 등록(분류, 제목, 내용, 긴급도) / 내 문의 목록·상세(상태·댓글) / 관리자 전체 목록(상태·분류 필터, 상태 변경) / 댓글.
- 담당자 필드는 두지 않는다. 상태를 바꾼 사람과 댓글 작성자가 처리 이력을 대신한다.
- 챗봇 연계: 챗봇이 규정을 모를 때 "헬프데스크에 문의하기" 링크를 보여 준다. 고장·계정 요청은 챗봇이 문의 등록을 제안하고 확인 버튼을 누르면 등록한다(7.3).

## 10. 구현 순서 (Cursor)
1. 프로젝트 생성, DB 스키마·권한 규칙(supabase/migrations), 이메일 로그인, 역할
2. 회의실 예약 (중복 방지 DB 규칙 포함)
3. 헬프데스크
4. 챗봇: 규정 적재 스크립트 → 질의응답 화면 (LLM은 로컬 Ollama만 쓴다. 유료 LLM 호출 LLM_PROVIDER=claude는 사람 승인 전 거절)
5. 챗봇 고도화 1단계 (R-003): 실행 시각에 따라 실패하는 테스트 수정, 평가 자동화(7.4), 규정 재적재 명령 수정, 규정 데이터 정리(7.1), 업무 분류·날짜 해석과 확인 후 저장(7.3), 업무 결과의 LLM 재작성 제거. 작업 가이드: docs/handoff/requests/ax-office-tools_Cursor작업가이드_Claude.md
6. 챗봇 고도화 2단계 (R-004): pgvector 설치, 임베딩 테이블(마이그레이션 0005), 임베딩 스크립트, 혼합 검색과 되돌아가기(7.5), 평가 혼합 모드(7.4). 작업 가이드 4장
7. 3단계 이후(답변 품질, 시연 자료)는 단계마다 이 설계서를 먼저 고친 뒤 별도 요청한다.

## 11. 검수 확인 항목
- [ ] 챗봇: 규정에 없는 질문에 지어내지 않고 확인 불가 문장으로 답하는가
- [ ] 챗봇: 모든 답변에 문서명·조항·기준일이 붙는가
- [ ] 예약: 같은 방의 겹치는 시간 두 건을 동시에 눌러도 한 건만 들어가는가
- [ ] 예약·문의: 남의 것을 수정·취소할 수 없는가
- [ ] 문의: 상태가 접수 → 처리중 → 완료 순서로만 바뀌는가
- [ ] 공통: API 키가 화면 코드·저장소에 노출되지 않는가
- [ ] 챗봇: 규정을 묻는 문장이 예약·문의로 처리되지 않는가 (평가 질문 34개 모두)
- [ ] 챗봇: 확인 버튼을 누르기 전에는 예약·취소·문의가 DB에 반영되지 않는가
- [ ] 챗봇: 날짜 해석이 7.3 규칙대로인가 (R-003 합격 표)
- [ ] 테스트: 실행 시각과 관계없이 모두 통과하는가
- [ ] 검색: 혼합 검색이 7.4 완료 기준을 넘는가, 검수용 별도 질문 20개에서도 비슷한가
- [ ] 검색: Ollama를 끄거나 임베딩이 없을 때 키워드 검색으로 답하고 오류가 나지 않는가
- [ ] 검색: 직원 권한으로 임베딩 테이블을 바꿀 수 없는가, 임베딩 호출이 이 PC 주소로만 가는가
