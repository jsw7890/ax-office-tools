# 설계서: 사내 챗봇 · 회의실 예약 · 헬프데스크 (최소 기능 버전)

상태: v0.1 설계 완료 (Claude 단독 설계) / 원본: Claude Docs 설계서(2026-11-06)
Cursor는 이 문서를 고치지 않는다. 설계와 달라지는 필요가 생기면 docs/handoff/requests/ 에 요청 파일로 알린다.

## 1. 목적과 원칙
- 직원 약 50명이 쓰는 웹앱 하나에 세 기능을 최소 기능으로 만든다. 취업용 레퍼런스이므로 실제 회사 데이터는 쓰지 않는다.
- 한 앱 · 한 DB · 한 로그인을 공유한다. 그래야 챗봇이 회의실·문의 데이터를 읽을 수 있다.
- 3장에 적은 "하지 않는 것"은 만들지 않는다.
- 비용 발생(LLM 호출 포함), 비밀키, 보안 설정, 배포는 사람 승인 없이 하지 않는다.

## 2. 기술 선택 (제안, 검수 때 확정)
| 구성 | 선택 |
| --- | --- |
| 화면 + 서버 | Next.js 웹앱 |
| DB · 로그인 · 권한 | Supabase (이메일 로그인, 행 단위 권한 RLS) |
| 배포 | Vercel (상용 배포는 사람 승인) |
| 챗봇 LLM | Claude API (서버에서만 호출) |

## 3. 범위
| 모듈 | 하는 일 | 하지 않는 일 |
| --- | --- | --- |
| 사내 챗봇 | 규정 질문에 답하고 근거 조항 표시 | 규정 외 질문, 실제 사내 문서 학습, 대화 기억 |
| 회의실 예약 | 방별 시간표, 예약·취소, 중복 방지 | 반복 예약, 승인, 장비 예약, 알림, 캘린더 연동 |
| 헬프데스크 | 문의 접수, 상태 관리, 댓글 | 담당자 자동 배정, SLA, 첨부파일, 메일 알림, 자산 연동 |
공통으로 뺀 것: 알림, 통계 대시보드, 다국어, 실제 회사 규정 사용.

## 4. 폴더 구조
```
docs/        design.md, RULES.md, handoff/
src/         앱 코드 (Cursor)
supabase/    migrations/ (DB 스키마·권한 규칙)
data/regulations/  규정 원문 텍스트와 출처 기록
tests/       테스트 (Cursor)
```

## 5. 공통: 로그인과 권한
- 이메일 로그인 필수. 역할은 staff(직원), admin(관리자) 둘뿐. admin은 총무 등 문의를 받는 사람으로 가정한다.
- 권한 규칙은 화면이 아니라 DB(RLS)로 건다.
  - 직원: 예약·문의는 본인 것만 수정·취소. 시간표 표시를 위해 예약 목록은 전체 조회 가능.
  - 관리자: 방 관리, 전체 문의 조회·상태 변경, 전체 예약 취소.
- API 키는 서버 환경변수에만 둔다. 화면 코드·저장소에 넣지 않는다.

## 6. 데이터 모델
| 테이블 | 컬럼 |
| --- | --- |
| profiles | id(로그인 사용자 id), name, email, role(staff/admin), created_at |
| regulation_docs | id, title, publisher, source_url, base_date, is_sample(기본 true), created_at |
| regulation_chunks | id, doc_id, article_no, heading, content, sort_order |
| chat_logs | id, user_id, question, answer, cited_chunk_ids, created_at |
| rooms | id, name, capacity, location, active |
| reservations | id, room_id, user_id, title, start_at, end_at, status(active/cancelled), created_at |
| tickets | id, requester_id, category(pc/account/printer_network/etc), title, description, urgency(normal/urgent), status(received/in_progress/done), created_at, updated_at, done_at |
| ticket_comments | id, ticket_id, author_id, body, created_at |
- 중복 예약 방지는 DB 규칙으로 건다: 같은 room_id에서 status=active인 예약의 시간 범위가 겹치면 저장 거부(Postgres 시간 범위 배제 제약). 두 사람이 동시에 눌러도 한 건만 저장돼야 한다.
- 질문 로그에는 이름 대신 user_id만 남긴다. 보관 기간은 사람이 정한다(미정).

## 7. 사내 챗봇
### 7.1 규정 자료
- 출처가 분명한 공개 자료만 쓴다. 후보: 고용노동부 표준취업규칙, 국가법령정보센터의 근로기준법 조문. 원문을 내려받아 이용 조건을 확인한 뒤 data/regulations/ 에 텍스트로 저장한다.
- 문서마다 regulation_docs에 발행처·URL·기준일을 기록한다. is_sample=true.
- 화면에 "공개 자료 기반 샘플이며 실제 회사 규정이 아닙니다 / 법률 자문이 아닌 참고용 / 고객·개인정보는 입력하지 마세요"를 상시 표시한다.
- 조항 단위로 쪼개 regulation_chunks에 넣는다(article_no, heading, content).

### 7.2 동작
1. 직원이 질문 한 개 입력 (대화 기억 없음, 질문 하나당 답 하나).
2. 서버가 질문과 관련된 조항을 LLM에 전달한다. 규정 분량이 작으면 전체 조항을 전달하는 가장 단순한 방식으로 시작한다. 분량·비용 문제가 생기면 키워드 검색으로 후보 조항만 전달하도록 요청 파일로 알린다.
3. LLM은 전달된 조항만 근거로 답하고 문서명·조항 번호를 붙인다.
4. 근거가 없으면 정확히 이 문장으로 답한다: "규정에서 확인되지 않습니다. 관리자에게 문의하세요." 추측하지 않는다.
5. 규정과 무관한 질문은 "규정 질문만 답할 수 있어요."로 안내한다.
6. 답변 아래에 출처 문서·조항·기준일을 표시하고 chat_logs에 저장한다.
- 사용자별 하루 질문 수를 제한한다. 기본값 20회(가정, 사람이 조정).
- 챗봇 코드는 "도구" 추가가 쉬운 구조로 만든다. 도구는 이번 버전에서 구현하지 않는다(9.5 선택 단계 제외).

## 8. 회의실 예약
- 운영 시간 09:00–18:00, 30분 단위 (확정). 종료 > 시작, 예약은 하루 안에서만. 지난 시간은 예약 불가. 본인 예약만 취소(관리자는 전체).
- 화면: 시간표(날짜 선택, 방 × 시간 격자, 예약자 표시) / 예약 입력 창(방·시간 채워짐, 제목 입력) / 내 예약(목록, 취소) / 관리자 방 관리(이름·수용 인원·위치·사용 여부).
- 방 개수는 미정. 샘플 데이터로 3개 방을 넣는다.

## 9. 헬프데스크
- 상태는 접수 → 처리중 → 완료. 완료 후 되돌리지 않고 새 문의를 등록한다. 완료 시 done_at 기록.
- 화면: 문의 등록(분류, 제목, 내용, 긴급도) / 내 문의 목록·상세(상태·댓글) / 관리자 전체 목록(상태·분류 필터, 상태 변경) / 댓글.
- 담당자 필드는 두지 않는다. 상태를 바꾼 사람과 댓글 작성자가 처리 이력을 대신한다.
- 챗봇 연계(이번 버전): 챗봇이 규정을 모를 때 "헬프데스크에 문의하기" 링크만 보여 준다.

## 10. 구현 순서 (Cursor)
1. 프로젝트 생성, DB 스키마·권한 규칙(supabase/migrations), 이메일 로그인, 역할
2. 회의실 예약 (중복 방지 DB 규칙 포함)
3. 헬프데스크
4. 챗봇: 규정 적재 스크립트 → 질의응답 화면 (LLM 호출은 사람 승인 후)
5. (선택, 설계서 확정 후 별도 요청) 챗봇의 회의실 현황 조회: 읽기 전용 도구 하나. 예약 확정은 화면에서만.

## 11. 검수 확인 항목
- [ ] 챗봇: 규정에 없는 질문에 지어내지 않고 확인 불가 문장으로 답하는가
- [ ] 챗봇: 모든 답변에 문서명·조항·기준일이 붙는가
- [ ] 예약: 같은 방의 겹치는 시간 두 건을 동시에 눌러도 한 건만 들어가는가
- [ ] 예약·문의: 남의 것을 수정·취소할 수 없는가
- [ ] 문의: 상태가 접수 → 처리중 → 완료 순서로만 바뀌는가
- [ ] 공통: API 키가 화면 코드·저장소에 노출되지 않는가

## 12. 열린 이슈
- 규정 원문 이용 조건 확인 (후보는 확정, 원문 확보 때 확인)
